# Project Insight Report

صديقي لدي مشروعي هذا واريد منك اولا "أريدك في هذه المرحلة أن تتوقف تمامًا عن البرمجة أو تعديل أو حذف أي شيء في المشروع.

مهمتك الأولى فقط هي **فهم المشروع بالكامل وتحليله تحليلًا عميقًا وشاملًا** قبل أن نبدأ بأي تطوير.

تعامل مع المشروع وكأنك استلمت مشروعًا من فريق تطوير آخر وتحتاج إلى فهمه بنسبة 100% قبل أن تلمس أي ملف.

## المطلوب منك

افحص المشروع بالكامل، واقرأ كل الملفات والمجلدات والشفرة والمكونات والموارد والإعدادات الموجودة فيه.

لا تكتفِ بإلقاء نظرة عامة على أسماء الملفات، بل حاول فهم **ما الذي يفعله كل جزء فعلًا، وكيف تتصل الأجزاء ببعضها**.

بعد الانتهاء من الفحص، أنشئ لي تقريرًا شاملاً جدًا عن المشروع.

### 1. نظرة عامة كاملة

اشرح لي:

* ما هو المشروع؟

* ما الهدف منه؟

* ما الذي يستطيع فعله حاليًا؟

* ما الذي تم تنفيذه بالفعل؟

* ما الذي يبدو أنه غير مكتمل؟

* ما هي الفكرة الأساسية وراء المشروع؟

* كيف يفترض أن يستخدمه المستخدم النهائي؟

* ما هي أهم الأنظمة الموجودة فيه؟

### 2. خريطة المشروع

أنشئ خريطة واضحة للمشروع توضّح:

* جميع المجلدات.

* جميع الملفات المهمة.

* وظيفة كل مجلد.

* وظيفة كل ملف.

* الملفات التي يعتمد عليها كل جزء.

* العلاقات بين الملفات.

* نقطة بداية تشغيل المشروع.

* أهم الملفات المركزية في المشروع.

أريد أن أعرف **أين يوجد كل شيء بالضبط**.

مثال على الأسلوب المطلوب:

`src/...`

→ مسؤول عن ...

`components/...`

→ يحتوي على ...

`X.tsx`

→ مسؤول عن ...

`Y.ts`

→ يتعامل مع ...

ولا تذكر الملفات لمجرد ذكرها؛ اشرح دورها الحقيقي.

### 3. تحليل الكود

حلل البنية البرمجية بالتفصيل:

* Architecture

* Components

* Functions

* Classes

* Hooks

* State management

* Data flow

* Event handling

* APIs

* Services

* Utilities

* Storage

* Configuration

* Dependencies

اشرح كيف تنتقل البيانات داخل المشروع.

مثلًا:

المستخدم يقوم بـ X

→ Component A

→ Function B

→ State C

→ Service D

→ النتيجة تظهر في Component E

أريد هذا النوع من الفهم، وليس مجرد وصف عام.

### 4. الأنظمة والميزات

حدد **كل نظام موجود في المشروع** واشرحه بالتفصيل.

لكل نظام أريد:

* اسمه.

* وظيفته.

* مكان وجوده في الملفات.

* الملفات التي تشغله.

* الملفات التي يعتمد عليها.

* كيف يبدأ.

* كيف يعمل.

* كيف يتفاعل مع الأنظمة الأخرى.

* ما الذي يحدث عندما يستخدمه المستخدم.

* هل هو مكتمل أم جزئي؟

* هل توجد مشاكل أو نقاط ضعف فيه؟

### 5. واجهة المستخدم

حلل الـ UI بالكامل:

* الصفحات.

* الشاشات.

* النوافذ.

* الأزرار.

* القوائم.

* النماذج.

* الـ HUD.

* الـ dialogs.

* التنقل.

* حالات التحميل.

* حالات الخطأ.

* الحالات الفارغة.

* responsive behavior.

وضح أين يوجد كل عنصر في الكود وكيف يعمل.

### 6. تجربة المستخدم

اشرح رحلة المستخدم الكاملة داخل المشروع.

ابدأ من:

**فتح المشروع**

ثم:

→ ماذا يرى؟

→ ماذا يستطيع أن يفعل؟

→ ماذا يحدث عند الضغط؟

→ كيف تنتقل البيانات؟

→ كيف تتغير الواجهة؟

→ ماذا يحدث في النهاية؟

أنشئ User Flow واضحًا.

### 7. البيانات والتخزين

حلل جميع البيانات:

* أين يتم تعريفها؟

* أين يتم تخزينها؟

* كيف يتم قراءتها؟

* كيف يتم تعديلها؟

* كيف يتم حذفها؟

* هل يوجد Local Storage؟

* هل يوجد Database؟

* هل يوجد API؟

* هل البيانات ثابتة أم ديناميكية؟

* ما هي الـ schemas أو types المستخدمة؟

### 8. المكتبات والتقنيات

حدد جميع التقنيات والمكتبات المستخدمة.

لكل واحدة اشرح:

* لماذا تستخدم؟

* أين تستخدم؟

* ما أهم وظائفها في المشروع؟

* هل هي ضرورية؟

* هل توجد مكتبات غير مستخدمة؟

* هل توجد dependencies يمكن الاستغناء عنها؟

### 9. الملفات المهمة جدًا

أنشئ قائمة مثل:

**Critical Files**

ثم رتب الملفات حسب أهميتها:

1. أهم ملف

2. ثاني أهم ملف

3. ثالث أهم ملف

   ...

واشرح لماذا كل ملف مهم.

### 10. المشاكل والمخاطر

ابحث عن:

* Bugs محتملة.

* أخطاء منطقية.

* مشاكل Architecture.

* تكرار في الكود.

* كود غير مستخدم.

* Dependencies غير ضرورية.

* مشاكل Performance.

* Memory leaks.

* مشاكل Security.

* مشاكل UX.

* مشاكل قابلية التوسع.

* أجزاء هشة يمكن أن تنكسر عند التعديل.

لكن **لا تصلح أي شيء الآن**.

فقط سجل المشكلة واشرحها.

### 11. الأشياء الناقصة

حدد بدقة:

* ما الذي يبدو أنه ناقص؟

* ما الذي تم عمله جزئيًا؟

* ما الذي يحتاج إلى إكمال؟

* ما الذي يحتاج إلى إعادة تصميم؟

* ما الذي يحتاج إلى تحسين؟

* ما الذي لا يعمل كما ينبغي؟

فرّق بوضوح بين:

**موجود ويعمل**

**موجود لكنه ناقص**

**موجود لكنه فيه مشكلة**

**غير موجود أصلًا**

### 19. أهم شيء: لا تخمّن

هذه نقطة مهمة جدًا.

لا تقل إن شيئًا موجود إذا لم تجده.

لا تفترض أن وظيفة معينة تعمل لمجرد وجود اسم لها.

فرّق دائمًا بين:

**وجدت هذا فعليًا في الكود**

و

**استنتجت أن هذا هو المقصود**

و

**هذا غير موجود حاليًا**

إذا لم تكن متأكدًا من شيء، قل إنك غير متأكد.

### 20. لا تعدّل المشروع

* إنشاء ملفات.

* حذف ملفات.

* تعديل ملفات.

* إعادة هيكلة المشروع.

* تثبيت مكتبات.

* تشغيل تغييرات تلقائية.

* إصلاح Bugs.

* إعادة تصميم UI.

**أريد التحليل فقط.**

بعد أن تنتهي من التحليل، لا تبدأ التطوير.

أريد منك أولًا أن تعطيني **تقريرًا شاملًا جدًا يمثل خريطة كاملة للمشروع، بحيث أستطيع أنا وأنت فهم المشروع ومعرفة أين يوجد كل شيء وكيف يعمل قبل أن نقرر ما الذي سنغيره.**

ابدأ بفحص المشروع بالكامل، ثم قدم التقرير من الأعلى إلى الأسفل، ولا تتجاوز أي جزء مهم.
